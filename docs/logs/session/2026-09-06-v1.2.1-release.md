## Version drift and the resolved version

The manifests declared `1.2.0` while the newest published release was `v1.0.1`.
Tracing `Cargo.toml` showed two candidate bumps that were never tagged or
published: `1.1.0` (`924744994`, 2026-08-23) and `1.2.0` (`b798da5f9`,
2026-09-01). `git ls-remote --tags` confirmed the remote carries only
`gosling-v1.0.0` and `v1.0.1-optimization-and-workspaces`; the many other local
`v1.0.x` tags are inherited goose tags, not gosling releases.

The drift is therefore explained, not ambiguous: two prepared-but-unreleased
candidates. Taking the canonical source (`1.2.0`) and the operator's explicit
"increment version", the bundled helper resolved the next version under the
declared scheme:

```sh
python3 <skill>/scripts/next_release_version.py --self-test   # OK
python3 <skill>/scripts/next_release_version.py 1.2.0         # 1.2.1
```

`v1.2.1` collided with no local tag, no remote tag, and no GitHub release.
`v1.2.1` supersedes both unpublished candidates; the `v1.1.0` candidate notes
are retained and marked superseded rather than deleted, and the noncanonical
`v1.0.1-optimization-and-workspaces` tag is preserved as published history.

## Defects found while preparing

### REL-CI-001 — tool dispatch dropped owner-prefixed names (fixed)

The repository's CI test gate had been failing on `main` since 2026-09-05. The
last green run was `add OpenAI format overrides and model metadata` (2026-09-04);
every run after it failed the same way, on `test_prompt_codemode`.

Cause: `04114c2c7` removed a fallback in
`ExtensionManager::resolve_tool` that resolved an owner-prefixed tool name
(`code_execution__list_functions`) against a live extension when the name was
not in the advertised list. Platform extensions advertise their tools
unprefixed, so after the removal a model addressing one by owner got
"Tool not found" and failed its turn. That commit's message does not mention
the removal; its stated subject is provider auth, permissions and session
handling.

Fixed in `043c70016` by restoring the fallback with a comment explaining why it
exists, plus
`test_resolve_tool_accepts_owner_prefixed_name_for_unprefixed_tool`, which
asserts both that a live owner resolves and that a prefix naming no extension
still fails. The pre-existing
`test_resolve_tool_error_includes_available_tools` is unaffected because its
probe name contains no `__`.

### REL-CI-002 — tests read the operator's real config (open, recorded)

With REL-CI-001 fixed, the local suite advanced past `acp_provider_test` and
surfaced two further failures that CI's fail-fast had been masking:

- `test_compaction_fires_before_first_llm_call` and
  `test_compaction_fires_inside_reply_loop` assert against the 0.8 default
  compaction threshold, but `check_if_compaction_needed` reads
  `GOSLING_AUTO_COMPACT_THRESHOLD` from the real `Config::global()`. This
  machine's `~/.config/gosling/config.yaml` sets `0.95`, which puts the 110,000
  of 128,000 fixture below the trigger, so the tests report that compaction
  never fired.
- Setting `GOSLING_AUTO_COMPACT_THRESHOLD=0.8` fixes those two and then breaks
  `test_custom_preferences_read_save_remove`, which asserts an exact preference
  list and sees an added `autoCompactThreshold` entry.

Both are the same defect class: integration tests reading operator state instead
of a fixture. Neither is a product regression, and both pass in CI, which has no
operator config. Recorded as open in `docs/TODO.md` with the repository's own
precedent for the fix (`93a19738d`, which isolated the summarizer-mode tests).
Not bundled into this release.

## Limits

Documentation preparation checks nothing automatically. The maintainer-owned
gates in `RELEASE_CHECKLIST.md` — installed Desktop acceptance on a clean
machine, signing and notarization, artifact and checksum verification, install
scripts, and the unauthenticated release readback — were not performed here and
are not claimed. The GitHub `signing` environment's Apple and Azure credentials
remain the documented blocker for a signed artifact.
